# femtochat × gradient-horizon: monorepo with Kaggle sync

Date: 2026-11-22
Status: design, ready for approval

## Intent

femtochat (code, experiments, results) and gradient-horizon (the blog that
writes about it) are two repos that describe one project. Today the code is
local-only with no remote, the blog is a public Jekyll/Chirpy repo deployed by
GitHub Actions, and the notebooks that run the Kaggle training live only in
Kaggle's web editor. Three copies of the truth, no mechanical link between
them.

Goal: one repo where the code, the results, the posts, and the Kaggle
notebooks live together, with a CLI script that moves notebooks and code
between the local checkout and Kaggle without either side silently
overwriting the other.

**Why now.** The next blog post is about the sweep. Writing it means quoting
numbers that live in `REPORT.md` and embedding figures that `make_figures.py`
generates. With the post in a different repo from both, the post can drift
from the numbers it cites, and nothing catches it.

**Who it serves.** The author first — this is a learning project, and the
writing is the accountability mechanism. A reader second: the published repo
should be navigable, with the code a post discusses findable from the post.

## Goals

- One repo holding code, results, posts, and notebooks, with one history.
- Notebooks stay editable in Kaggle's web editor next to the GPU.
- `sync_kaggle.sh` pushes/pulls/runs/fetches notebooks without clobbering
  the other side's edits.
- Blog deployment keeps working; code commits don't redeploy the site.
- Figures a post embeds are generated by `make_figures.py` and served by
  Jekyll, with no manual copying.

## Non-goals

- No change to the model, training loop, or sweep definitions.
- No new tests or CI beyond what deployment needs.
- No reorganisation of the existing two blog posts.
- No change to Kaggle kernel settings for the in-scope kernels (both are
  already `is_private: true`; that stays — the repo being public does not
  make the kernels public).
- No attempt to make the 1.6 GB of local state (`.venv`, corpus, `wandb/`,
  `output/`) portable or tracked.

## Anti-goals

- **A stale kernel left holding unversioned code.** Two of the four kernels
  are superseded, and each holds a training script that exists nowhere in
  git. Leaving them means the "three copies of the truth" problem survives
  the migration. This is why the two extras are an open decision rather
  than silently ignored.- **A sync script that guesses.** If both sides changed, it must stop and
  say so, not pick a winner.
- **A public repo containing a secret.** `.env` holds real `HF_TOKEN` and
  `WANDB_API_KEY` values. It is untracked today and must stay untracked.
- **A monorepo where `git add -A` commits a gigabyte.** The 1.6 GB of local
  state must be ignored before the first commit in the new layout.

## Constraints

- **gradient-horizon is public** (`github.com/lpossner/gradient-horizon`,
  no custom domain, served at `lpossner.github.io/gradient-horizon`).
  Merging femtochat in publishes `train.py`, the sweep definitions, and the
  six run logs. Confirmed acceptable.
- **Free-tier Pages cannot serve from a private repo**, so "monorepo with
  private code" is not available. This is why the public question was
  decisive rather than incidental.
- **Jekyll already excludes `docs` and `tools`** (`_config.yml:218`), so the
  exclude mechanism is established; femtochat needs one more entry.
- **CI builds at the repo root** and runs `htmlproofer` over `_site`
  (`pages-deploy.yml`). Anything not excluded and not a valid page will be
  scanned.
- **Kaggle CLI 2.2.4** is installed and authenticated as `lucasponer`
  (`~/.kaggle/kaggle.json`). It has no verb to run an already-uploaded
  kernel (see the script section).
- **Four kernels exist, not two.** Only two are in this design's scope:

  | ref | role |
  |---|---|
  | `tokenize-fineweb-edu-sample-10bt` | canonical tokenizer; `dataset_sources: [lucasponer/fineweb-edu-sample-10bt]` |
  | `train-fineweb-edu-sample-10bt-cuda` | canonical trainer; `kernel_sources: [lucasponer/tokenize-fineweb-edu-sample-10bt]` |
  | `train-fineweb-edu-sample-10bt` | older trainer, superseded by the CUDA one |
  | `tokenize-fineweb-sample-10bt` | points at `aarushmahajan/general-corpus`, an unrelated dataset |

- **The kernel chain is load-bearing.** The CUDA trainer reads its corpus
  from `/kaggle/input/notebooks/lucasponer/tokenize-fineweb-edu-sample-10bt/`.
  A push that drops `dataset_sources` or `kernel_sources` breaks the run in
  a way that looks like a data problem, not a metadata one.
- **`enable_internet: true` on the in-scope kernels.** Not required by this
  design, but already set and harmless.
- The in-scope kernels use a pinned `docker_image`; these must be preserved
  through push/pull.

## Approaches considered

**Where the post and its figures live** (decided in conversation):

- **Post in femtochat, publish into the blog.** Rejected: needs a copy step
  that can drift, and two repos stay in play.
- **Post in the blog, femtochat exports figures.** Rejected for the same
  reason — the post still can't see the numbers it cites.
- **Monorepo, post at root, code in `femtochat/`.** *Chosen.* The only
  option where a post and the code it describes share a history.

**How code reaches Kaggle — not a question.** `train.py` was written to run
the sweep experiments on the M1, and it stays there; nothing syncs it. The
Kaggle kernels are self-contained notebooks that own their own training
code, and the real training run is expected to diverge from the sweep. So
the sync script moves notebooks and nothing else.

**Consequence to accept:** the CUDA notebook embeds a training script copied
from `train.py` (a `%%writefile` cell writing `/kaggle/working/train.py`).
With no sync mechanism that copy is a permanent, unmanaged fork: changes to
`train.py` never reach Kaggle, and vice versa. This is intended — two
artefacts for two environments — but they will drift, and neither is the
other's source of truth.

## Design

### Layout

```
gradient-horizon/                      ← repo root (public, Pages)
├── _config.yml                        ← + femtochat in `exclude`
├── _posts/                            ← blog posts (existing)
├── _tabs/  _data/  _plugins/          ← Chirpy (existing)
├── assets/img/
│   ├── avatar.png                     ← existing
│   └── femtochat/                     ← figures, written by sync
├── tools/
│   ├── run.sh  test.sh                ← existing
│   └── sync_kaggle.sh                 ← new
├── docs/                              ← all design docs live here
│   ├── roadmap.md                     ← the 8-stage plan
│   └── specs/                         ← design docs, incl. this one
├── femtochat/                         ← excluded from Jekyll
│   ├── pyproject.toml  uv.lock
│   ├── train.py  sweep.py  make_figures.py
│   ├── REPORT.md                      ← results doc the post draws on
│   ├── figures/                       ← generated, tracked
│   ├── logs/                          ← the six kept run logs
│   └── notebooks/                     ← Kaggle-owned, one dir per kernel
│       ├── tokenize-fineweb-edu-sample-10bt/
│       │   ├── kernel-metadata.json
│       │   └── tokenize-fineweb-edu-sample-10bt.ipynb
│       └── train-fineweb-edu-sample-10bt-cuda/
│           ├── kernel-metadata.json
│           └── train-fineweb-edu-sample-10bt-cuda.ipynb
└── .github/workflows/pages-deploy.yml ← + paths-ignore
```

### Ownership rule

One rule, stated once, enforced by the script:

| Path | Owner | `push` | `pull` |
|---|---|---|---|
| `femtochat/**.py`, `pyproject.toml`, `uv.lock` | local, M1 only | never | never |
| `femtochat/notebooks/**` | Kaggle | uploads local → Kaggle | downloads Kaggle → local |
| `femtochat/figures/**`, `assets/img/femtochat/**` | local (generated) | — | — |

The script never touches `.py` files in either direction — they are not
part of the Kaggle loop at all.

The script refuses to overwrite either side without `--force`. It compares
the local file against the last-pulled copy (recorded as a hash in the
kernel dir) and against Kaggle's current version; if both moved, it stops
and names both.

### `sync_kaggle.sh`

Subcommands, all taking a kernel name (or `all`):

```
sync_kaggle.sh pull <kernel>     Kaggle -> local notebook + metadata
sync_kaggle.sh push <kernel>     local -> Kaggle, then trigger a run
sync_kaggle.sh status <kernel>   latest run status
sync_kaggle.sh output <kernel>   fetch run outputs to a local dir
sync_kaggle.sh figures           make_figures.py -> assets/img/femtochat/
```

There is deliberately no `run` subcommand. Kaggle CLI 2.2.4 has no verb that
triggers a run of an already-uploaded kernel: `kernels push` (alias
`update`) both uploads and runs, and its only options are `--path`,
`--timeout` and `--accelerator`. So "run what is already there" is not
expressible, and `push` always runs as a side effect.

Behaviour that matters:

- `push` never edits `kernel-metadata.json`'s `dataset_sources` or
  `kernel_sources` — those encode the chain.
- `pull` is the only thing that writes into `notebooks/`.
- `output` is restricted to the train kernels and refuses to run against a
  tokenize kernel. Its output is the tokenized corpus (`train.bin.gz`,
  `val.bin.gz`, `tokenizer_state.pkl`) — ~264 MB locally, and the input the
  downstream kernel consumes. Downloading it is never the intent, and the
  train kernels' outputs are the small artefacts a post needs. The script
  should also cap what it fetches, since a checkpoint is ~36 MB and run
  outputs accumulate.
- Every subcommand is non-interactive and exits non-zero on failure, so it
  can be scripted.
- No `.py` file is uploaded or downloaded by any subcommand.

### Figure pipeline

`make_figures.py` keeps writing `femtochat/figures/*.png` — unchanged, so
`REPORT.md`'s relative links keep working. `sync_kaggle.sh figures` copies
them to `assets/img/femtochat/`. Posts reference them with Jekyll's
`relative_url` filter so the `/gradient-horizon` baseurl is applied:

```
![Optimizer, initialization & weight tying]({{ '/assets/img/femtochat/sweep_optimizer_init.png' | relative_url }})
```

Figures are tracked in both locations: `femtochat/figures/` is the artefact
`REPORT.md` embeds, `assets/img/femtochat/` is what Jekyll serves. The copy
is mechanical, so drift is detectable with a hash comparison the script can
run.

### Deployment

`pages-deploy.yml` gains a `paths-ignore` for `femtochat/**`, `docs/**`, and
`tools/**` so a training or code commit does not rebuild the site. A manual
`workflow_dispatch` remains available, which it already has.

### Migration

The monorepo is the existing `gradient-horizon` repo — it keeps its history,
remote, and Pages setup. femtochat's 18 commits are grafted in so the
experiment history survives:

1. Point the local femtochat checkout at the blog repo as a remote (it has
   no remote today), then `git subtree add --prefix=femtochat` (or
   `git filter-repo` if subtree's squash is unacceptable).
2. Merge the two `.gitignore` files; femtochat's rules for `.venv`,
   `FineWeb-edu_sample_10BT/`, `wandb/`, `output/`, `.env` must all be
   present **before** the first commit in the new layout.
3. Move `logs/` under `femtochat/`, add `notebooks/` with pulled copies of
   the two in-scope kernels.
4. Collapse the docs convention: move the blog's
   `docs/superpowers/specs/2026-11-20-transformer-diagrams-design.md` and
   femtochat's `docs/specs/*` into the single root `docs/specs/`, and
   `roadmap.md` to `docs/`.

The old local femtochat directory is kept until the merged repo builds and
deploys, then deleted by hand.

## Decisions

### Decided by the author

- Monorepo, rather than two repos plus a publish step.
- Code may be public.
- Ownership is split by file type: `.py` local, notebooks Kaggle.
- The sweep is what the next post covers; the real training run may diverge
  from it, and that is acceptable.
- **One docs convention: `docs/specs/` at the repo root.** The blog's
  `docs/superpowers/specs/` is abandoned; `roadmap.md` and all design docs
  move under `docs/`.
- **`REPORT.md` lives in `femtochat/`** and stays a results document. The
  post draws on it rather than replacing it, so it is not rewritten into
  post prose.
- **The two superseded kernels are left in place.** They stay out of scope
  for the sync script, and their embedded training code stays unmanaged.
  Deleting them is irreversible on Kaggle's side and buys only tidiness, so
  leaving them is the lower-risk default.

### Calls made here, correctable

- `sync_kaggle.sh` is bash, living in `tools/` next to the existing scripts,
  rather than a Python module in `femtochat/`. It touches both trees, so
  neither side's toolchain is the obvious home.
- The monorepo is gradient-horizon, not femtochat — it keeps the remote and
  the Pages wiring.
- `femtochat/figures/` and `assets/img/femtochat/` both hold the PNGs, since
  `REPORT.md` and the posts each need a stable relative path.
- femtochat's history is preserved via subtree rather than a fresh import.
- The two training codebases (`train.py` on the M1, the script embedded in
  the CUDA notebook) are left as independent forks. Unifying them is a
  separate question from this design.

## Left to the builder

- Exact `git subtree` invocation and conflict handling if paths collide.
- How the script records each notebook's last-pulled hash, so it can tell a
  local edit from a Kaggle edit before overwriting either.
- Whether `output` results land under `femtochat/output/` (currently ignored)
  or a new tracked location for the artefacts a post needs.
- What, if anything, to do about the two training codebases being forks —
  or whether to document the fork and move on.
